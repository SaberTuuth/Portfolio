Pathfinding Simulator

About Path Finder Simulation

I developed an interactive pathfinding and procedural maze generation tool in Java that visualizes graph traversal algorithms across multiple grid topologies (square, hexagonal, and triangular) while supporting real-time user editing.

Project Information

Genre: Automation | Simulation
Role: Full-Stack Developer
Team-Size: 1
Development Time: In Development
software/language: Intellij IDEA GitHub Java JavaFX

Introduction

Pathfinding algorithms are widely used in games and software navigation systems, but their behavior is difficult to understand from pseudocode alone. While learning graph traversal, I found that most examples demonstrated only the final path and did not show how the algorithm actually explored the search space or why different approaches produced dramatically different performance.

I created this tool to visualize the decision-making process of search algorithms in real time. By allowing the environment to be edited while the search runs and supporting multiple grid types, the application makes it possible to observe how node expansion, branching behavior, and heuristics affect the pathfinding process. The project was intended both as a learning exercise and as a debugging tool to better understand algorithm efficiency and tradeoffs.

Key Technical Challenges

1. Mapping Mouse Input to Grid Coordinates

The application supports square, hexagonal, and triangular grids, each with different geometric layouts and neighbor relationships. Converting continuous mouse coordinates into the correct tile required implementing separate coordinate calculations and hit detection logic for each grid type while ensuring accuracy during drag input.

2. Real-Time Editing and Drag Interaction

Allowing users to paint walls and weighted terrain by dragging the mouse introduced challenges with event handling and state management. I implemented a press–drag–release input system and prevented duplicate tile updates while maintaining responsiveness during rapid cursor movement.

3. Preventing UI Freezing During Search

Running search algorithms in a loop initially caused the JavaFX UI to freeze. To solve this, I converted the algorithms into step-based updates driven by a timed update loop, allowing the search to run incrementally while the interface remained interactive and observable.

4. Maintaining Correct Search State

The grid can be edited while the program is running, which required carefully resetting visited nodes, frontier structures, and reconstructed paths whenever the environment changed. This ensured algorithms always operated on a valid and consistent state.

5. Visualizing Algorithm Behavior

Simply finding a path was not sufficient; the goal was to observe algorithm decisions. I implemented node expansion visualization, frontier tracking, and path reconstruction so users could see how each algorithm explored the search space and why different approaches produced different results.

6. Procedural Maze Generation

I implemented a recursive backtracker maze generator using a depth-first search stack. The generator carves passages between cells by removing walls and runs step-by-step so the construction process can be observed. The generated maze can then be solved using A*, demonstrating the relationship between procedural generation and pathfinding.

Algorithm Behavior & Tradeoffs

The application implements multiple search strategies so their behavior can be compared under the same conditions.

Breadth-First Search (BFS)

BFS explores the grid uniformly outward from the start position and guarantees the shortest path in unweighted environments. However, it expands a large number of nodes, especially in open areas, making it inefficient for large maps.

Depth-First Search (DFS)

DFS prioritizes depth over coverage and uses very little memory, but it often explores long incorrect paths before backtracking. It does not guarantee the shortest path and performs poorly in open spaces. **Greedy Best-First Search** Greedy search prioritizes nodes closest to the goal using a heuristic distance estimate. It often reaches the goal quickly but can produce suboptimal paths because it ignores the actual travel cost and may get trapped exploring around obstacles.

Greedy Best-First Search

Greedy Best-First Search selects the next node to explore based solely on the heuristic estimate of distance to the goal. By always prioritizing the tile that appears closest to the target, it typically reaches the goal faster than uninformed searches. However, because it ignores the actual movement cost and previously traveled distance, it does not guarantee an optimal path. In environments with obstacles or weighted terrain, the algorithm often commits to poor routes and spends additional time correcting its decisions while navigating around barriers.

Uniform Cost Search (Dijkstra’s Algorithm)

Uniform cost search expands nodes based on accumulated movement cost and correctly handles weighted terrain. It always finds the lowest-cost path but explores many unnecessary nodes because it has no directional guidance toward the goal.

A* Search

A* combines the actual travel cost with a heuristic estimate to the goal. This allows it to prioritize promising directions while still guaranteeing the optimal path. In testing, A* consistently explored far fewer nodes and solved complex mazes significantly faster than the other algorithms.

Visualizing the node expansion made the differences clear: uninformed searches spread across the map, greedy search rushes toward the goal but makes mistakes, and A* balances exploration and direction to minimize total search cost.

What I Learned

This project taught me that algorithm performance is not only determined by execution speed but by how efficiently the search space is explored. Visualization revealed that heuristics have a greater impact on performance than raw processing speed, especially as grid size increases.

I also learned the importance of separating simulation logic from rendering. Running the algorithm in a tight loop caused the UI to freeze, which required redesigning the search to operate as incremental steps driven by a timed update loop.

Finally, building an interactive tool highlighted how input handling and state management become significantly more complex when a system must remain correct while the environment changes in real time.
